# Agent Release 规范

起草日期：2026-10-17。更新日期：2026-10-23。适用对象：为 Pactick 准备、核验、上传或发布 GitHub Release 的 Agent。

本规范是 Agent 执行 Release 任务必须遵守的项目规则，规定执行顺序、交付物和完成条件。本文不记录某个版本已经通过的验收，也不授予推送或发布权限。具体构建、签名和验收操作分别见[构建指南](BUILDING.md)、[Android 签名指南](ANDROID_SIGNING.md)、[发行流程](RELEASING.md)和[发布验收计划](RELEASE_AND_PROMOTION_PLAN.md)。

## 1. 确定任务范围和授权

Agent 开始工作时必须阅读当前工作目录适用的 `AGENTS.md`（如有），识别用户要求的目标状态。用户在当前会话中的明确指令优先于本文；已有授权在同一任务内继续有效。

| 用户要求 | Agent 应完成的工作 | 停止位置 |
| --- | --- | --- |
| 起草规范或 Release 说明 | 编写本地文档，核对实现和已有证据 | 交付文档，不创建远端 Release |
| 准备发布、构建候选包 | 准备源码、检查、构建、校验和说明 | 交付本地候选；远端操作须在已有授权内 |
| 创建指定 Release 草稿 | 核验来源和附件，创建远端草稿并上传约定制品 | 保持 `draft=true` |
| 发布指定版本 | 连续完成该范围内必要的准备、检查、源码及标签推送、上传、发布和回读核验 | 达到约定发布状态并报告结果 |

“发布指定版本”要求目标仓库、源码范围和发布类型能够从本次指令或会话中确定。不得因此改变仓库可见性、重写历史、移动已有标签、轮换签名密钥或执行线上部署。用户要求保持私有、只创建草稿或禁止设备操作时，必须遵守。

授权明确后，不为同一范围的每一步重复请求确认。确有缺失时，先完成不依赖该信息的准备工作，再针对具体仓库、提交、发布类型或缺项提问。请求批准发布前，应提供可审阅的版本、提交、附件清单、说明和未完成事项。

Release 正文和附件只允许包含第 5、6 节列明且适用于本次范围的标准内容。规范以外的内容，除非用户明确注明本次 Release 必须添加该具体项，否则不得擅自加入。该要求同时适用于草稿、预发布、正式发布，以及已有 Release 的后续编辑。

用户要求添加某项时，例外只适用于该项，不扩展到其他文件、报告或段落。一般性的“发布 Release”“整理完整”、用户未提出异议、历史附件、模板和工具输出，都不能作为增加内容的依据。未要求的可选内容直接省略，不以补充报告为由反复请求确认。

必须分别记录下列状态，不能相互替代：

- 仓库可见性：`private` 或 `public`。
- Release 状态：草稿或已发布。
- 发布类型：预发布或正式发布。
- Latest 标记：本次是否要求更新。

已发布的私有仓库 Release 只对有权访问该仓库的读者可见；`prerelease=true` 表示预发布类型，不表示私有或未发布。预览版默认不设为 Latest；正式版是否更新 Latest 按本次发布安排执行。

## 2. 核对当前源码和远端状态

在仓库根目录开始检查。下列命令只用于读取本地状态，不推送内容：

```powershell
git status --short
git diff --stat
git diff --cached --stat
git remote
git log -5 --oneline
git tag --list
```

上述 `git remote` 只列出 remote 名称。核对其实际地址时，先隐藏可能存在的凭据，再输出到日志或交付说明。访问远端前确认目标仓库身份；不能只依赖本地目录名或默认 remote。

Agent 必须核对：

1. 用户已有修改、未跟踪文件和本次发布所需改动。不得自动丢弃、提交或夹带无关修改；无法明确归属时使用独立工作目录整理候选。
2. `client/pubspec.yaml`、`CHANGELOG.md`、数据库迁移、构建脚本和工作流是否对应本次范围。未经明确要求，不修改人工维护的 `README.md`。
3. 远端仓库可见性、默认分支、同名标签及 Release 是否存在。存在时先读取标签提交、Release ID、状态和附件；不得直接覆盖。
4. 最终发布标签所指的完整提交，以及对应 Checks 的提交和结果。不能用默认分支最新一次成功替代发布提交的结果。
5. 发布条件是否来自当前实现、有效验证记录或尚未实施的计划。其他分支、旧工作目录和历史 Release 的功能、附件数量及测试结果不得直接沿用。

当前仓库的自动化入口如下；执行时应重新阅读对应文件，不能把本表当作永久不变的工具规格。

| 入口 | 当前行为 | 仍需另行完成的工作 |
| --- | --- | --- |
| [Checks](../.github/workflows/checks.yml) | 检查允许列表源码副本、Python 脚本、Go、PostgreSQL 集成场景、部署脚本及 Flutter debug 构建 | 正式签名、真机、正式制品来源及发布状态核验 |
| [Android 候选工作流](../.github/workflows/android-release.yml) | 从默认分支手动触发，检出已有标签，使用 `android-release` 环境构建签名 APK，上传 `android-release-candidate` Actions artifact | 仓库环境保护配置核对、人工验收及 GitHub Release 创建和发布 |
| [源码快照工具](../scripts/prepare_public_source.py) | 复制允许列表文件，执行启发式扫描，生成 manifest；目标目录必须不存在 | 全部发行内容审阅、实际 Git 文件和历史检查 |
| [来源校验工具](../scripts/verify_release_source.py) | 校验版本、许可证、manifest 文件及来源元数据一致性 | Git 提交与这些文件的真实对应关系、历史构建号和签名证书比较 |
| [部署升级脚本](../deploy/scripts/release.sh) | 对服务器执行备份、迁移和 API 升级 | 需要单独的部署任务；不得作为创建 GitHub Release 的常规步骤运行 |

当前候选工作流不生成 Windows/Linux 服务端发行包。新增平台、服务端管理程序或其他制品前，必须先确认对应源码、构建入口及验收要求已经存在，不能根据计划补写下载项。

## 3. 固定版本和源码来源

每次发布应在维护记录中确定目标仓库、上一版、本次标签、完整提交、客户端版本、Android 构建号、制品范围和发布类型。建议将本次工作记录保存在 `output/release-<tag>/RELEASE_RECORD.md`；该路径用于维护记录，不作为源码提交内容。

- 标签格式为 `vMAJOR.MINOR.PATCH[-suffix]`，必须等于 `client/pubspec.yaml` 中 `+buildNumber` 之前的版本加前缀 `v`。`preview`、`alpha`、`beta`、`rc` 等版本使用预发布类型，除非用户另有明确安排。
- Android 构建号必须为正整数；同包名更新时必须高于上一版。来源校验脚本只检查正整数，不比较历史版本。
- 根目录 `LICENSE` 与 `client/LICENSE` 必须逐字节相同。第三方材料的授权和通知要求另行核验。
- 标签必须指向确定的完整提交。不得让发布工具从默认分支临时创建标签；不得为通过校验而移动已发布标签。
- `SOURCE_COMMIT.txt`、`RELEASE_SOURCE.json`、说明和维护记录必须使用同一发布提交。不能把本地私人仓库提交写成发行仓库中不存在的标签提交。

已有发行仓库应从选定提交的干净检出生成快照。首次从私人工作目录导出源码时，先审阅允许列表快照并建立发行提交，再从该发行提交生成最终快照。维护记录可另列原始工作目录提交，但必须与发布提交区分。

`verify_release_source.py --commit` 接受调用者传入的完整 Git 对象 ID；格式通过不证明该提交对应快照。Agent 必须比较标签实际解析的提交，并从该提交生成快照，不能仅填入预期字符串。

源码归档必须在依赖下载和签名配置进入快照前生成。后续构建使用同一快照；构建前后按工作流使用 `--expected-metadata` 复核。`--allow-generated-files` 仅允许脚本列出的生成文件，不允许修改 manifest 中的源文件、许可证或锁文件。

任何进入发行内容的修改都必须重新生成快照和 manifest；影响二进制的修改必须重新构建、签名并核验。不得将新源码包与旧 APK 拼为同一候选。仅修改远端 Release 说明时无需重建二进制，但必须回读说明并确认附件未变。

## 4. 执行适用于本次范围的检查

检查命令和环境设置以[构建指南](BUILDING.md)及选定提交中的工作流为准。必须保存执行日期、提交、命令、工具版本、环境和结果，不能仅记录“全部通过”。

| 检查范围 | 必须记录的结果 | 结果的适用限制 |
| --- | --- | --- |
| 源码及脚本 | Python 检查、第三方通知检查、允许列表扫描、manifest 和实际 Git 文件审阅 | `prepare_public_source.py --check` 不扫描整个目录或 Git 历史，也不审阅图片与 JAR 内容 |
| Go 服务端 | 模块校验、测试、vet、构建；数据库集成测试的真实执行情况 | 未设置 `PACTICK_TEST_DATABASE_URL` 时 PostgreSQL 测试会跳过，不能记为通过；只使用隔离测试数据库 |
| Flutter 客户端 | 锁文件约束下的依赖安装、analyze、test 和所需构建 | debug APK、组件测试和截图不能替代正式 APK 的设备验收 |
| 最终 APK | 包名、版本、构建号、签名验证、证书指纹、APK SHA-256、内嵌许可及实际运行时依赖 | `apksigner` 通过不证明已安装、覆盖更新、后台通知或双设备同步正常 |
| 分发审阅 | 适用范围、素材来源、第三方条款及对应最终制品的审阅记录 | 证据采集器的 `completed_legal_audit: false` 不表示审阅完成；不以更新哈希代替处理差异 |
| 真机和部署 | 对应[发行流程](RELEASING.md)与专项清单的验收记录 | LAN/debug、模拟脚本或编译结果不能写成正式包、公网 HTTPS/WSS 或真实服务器验收 |
| 远端 CI | 对应完整提交的工作流链接及最终结论 | 排队、运行中、取消、失败和必需项目跳过均不记为成功 |

当前任务提醒相关改动按 [Android 任务提醒专项清单](ANDROID_TASK_REMINDER_CHECKLIST.md)验收。测试设备时，只能在本次授权范围内操作 Pactick；不得通过 ADB 查看其他应用或文件，系统界面、解锁、网络和权限操作由用户处理。

正式签名必须继续使用已确认的长期密钥，比较历史证书指纹并验证最终 APK。不得用 debug 签名补齐缺失的 release 配置，不得为解决覆盖安装问题卸载持有唯一数据副本的应用。签名配置、备份及证书不一致时的处理见[签名指南](ANDROID_SIGNING.md)和[发行流程](RELEASING.md)。

检查失败时，保留失败记录并处理原因；修正后重跑受影响的检查。环境不可用或用户禁止执行时，记录“未执行”及原因。预发布标记不会自动豁免验收；若用户明确接受部分验收尚未完成的预览分发，记录获准范围和缺项，不将其改记为通过。缺项未获准时，可继续交付本地候选或已授权的草稿。

## 5. 整理附件并生成校验和

源码仓库保存源码、脚本、测试和可公开文档。APK、AAB、可执行文件、安装包和构建归档作为 Release 附件分发，不提交到源码仓库；受审阅的构建依赖等例外按现有允许列表处理，例如 Gradle wrapper JAR。

下表列出标准附件范围，只选取与本次发布要求相符的制品。不得因为工作流生成了某个文件，就将其列为 Release 附件。

| 标准附件 | 适用范围与要求 |
| --- | --- |
| 源码归档 | 提供审阅后的允许列表源码；`SOURCE_MANIFEST.json` 保留在归档内部，与来源元数据对应，默认不单独上传 |
| APK | 包含 Android 分发时；必须是最终校验的同一文件。工作流当前输出 `pactick.apk`，可以在上传前改为含版本和构建号的文件名 |
| 其他平台安装包或可执行包 | 本次明确包含相应平台分发，且源码、构建入口和验收要求均已具备时提供；不得附加未要求的平台或工具 |
| `SHA256SUMS.txt` | 覆盖最终上传的其他附件，使用最终文件名；不包含该校验文件自身 |

原始 JSON 用于工具处理，不能代替给使用者阅读的发布说明。默认不得在 Release 正文粘贴原始 JSON、JSON 代码块或接口响应，也不得将 `.json`、`.jsonl` 等机器记录作为独立附件上传。该要求包括 `RELEASE_SOURCE.json`、`SOURCE_MANIFEST.json`、`THIRD_PARTY_NOTICES.json`、`FLUTTER_TOOLCHAIN.json`、`DISTRIBUTION_REVIEW.json` 及同类文件。只有用户明确注明本次 Release 必须包含某个具体 JSON 文件或原文时，才能对该项例外处理。

源码归档中项目本身需要的 JSON 配置、元数据以及生成的 `SOURCE_MANIFEST.json` 保留原有结构，不作为独立下载项。不得为绕过本规范，将额外的内部 JSON、报告或日志改名、转换格式、打包成新附件，或塞入源码归档。

下列材料仍须按原流程生成和核验，但默认只供维护和候选审阅，不直接发布到 Release：

| 维护材料 | 保存和使用方式 |
| --- | --- |
| `SOURCE_COMMIT.txt`、`RELEASE_SOURCE.json` | 保存完整提交、标签、版本、构建号及来源哈希；Release 正文只写必要的来源字段 |
| `APK_SIGNING_CERTIFICATE.txt` | 保存完整签名验证输出；Release 正文只写证书 SHA-256 指纹等必要结论 |
| 工具链和运行时依赖记录 | 保存实际工具版本、依赖清单及采集结果，供来源与构建复核使用 |
| 分发审阅记录、验证报告和详细日志 | 保存审阅依据与检查证据；Release 正文仅按第 6 节概括已验证事项、限制和已知问题，不上传完整报告 |

第三方声明、许可正文和必要 NOTICE 必须随源码归档或安装包按分发要求提供；独立上传声明 JSON 或内审报告不能替代通知义务。本次附件范围无法满足许可要求时，应说明缺项并等待用户明确处理范围，不得自行增加附件或删除必要通知。

打包后先核对归档内容，排除 keystore、`key.properties`、真实环境配置、数据库、备份、令牌、私人部署资料和测试日志。GitHub 自动生成的 Source code 链接不能替代经审阅的源码归档及其 manifest。

附件清单必须记录每项的本地位置、最终文件名、用途、字节大小、SHA-256 和纳入依据。纳入依据只能是本节列明的标准附件及其适用条件，或用户明确要求必须添加该具体项的指令；不能写成“便于审计”“工具已生成”或其他 Agent 自行判断的理由。该清单保存在维护记录中，不自动成为 Release 附件。

重命名后更新清单和 `SHA256SUMS.txt`；重新压缩、签名或修改内容后重新计算哈希。校验和不能证明发布者身份或分发授权。

不得用整个工作目录、`output/` 或 Actions artifact 目录的通配符直接上传。先按明确清单选取文件；附件总数以本次范围为准，不能沿用历史数量。

## 6. 编写面向使用者的 Release 说明

Release 正文使用便于阅读的中文段落、列表或表格，说明本版改了什么、下载哪个文件、如何安装或升级，以及哪些情况尚未验证。所有功能和验证结论必须对应本次源码及最终制品。正文标准范围限于下列内容；其他主题只有在用户明确要求本次必须添加时才能加入。

- 写明版本、发布类型、主要变化和影响使用的修复；计划功能不得写成已提供。
- 说明 Android 包名、最低系统要求、同包更新的签名与构建号要求；涉及改名或数据迁移时链接操作指南。
- 列出实际提供的平台、架构、附件用途和必要运行依赖。不存在的安装包或 GUI 不写入下载说明。
- 保留已知问题、未验证场景、数据迁移限制和影响使用的故障。构建、签名和真机结果分别表述。
- 提供最终 APK SHA-256、签名证书 SHA-256 指纹及校验和文件入口。说明当前客户端通过外部浏览器打开发布页，不自动校验 APK 完整性或证书。
- 描述功能时保留本地优先、同步可选的现状；源码预览和服务器程序下载不等于推荐公网部署。
- 链接入门、许可、第三方声明、问题反馈和私下安全报告入口。不得把私人路径、地址、凭据或内部日志放入公开说明。

公开说明不记录与使用者决策无关的 Agent 操作过程、构建重试、内部杀毒告警或排查过程。若问题确实影响附件可用性、完整性或安全性，应在处理后说明影响和处置结果，不能以删去内部记录代替修复。

需要引用内部 JSON 或日志中的检查结果时，只提取上述标准范围内的结论，改写为可读说明。不得用原始数据、完整测试清单、内部审阅报告或将其逐项改写后的长文扩展 Release 内容。

以下结构可按本次范围删减；删除占位内容后再用于发布：

```markdown
# Pactick <版本>（预发布或正式版）

## 本版变化

- <本版实际提供的功能或修复>

## 下载与安装

| 文件 | 平台或用途 | 安装、升级或运行要求 |
| --- | --- | --- |
| <实际附件名> | <平台及架构> | <必要条件与操作文档> |

## 已验证事项与限制

- <针对本次制品已经完成的检查>
- <未验证场景、已知问题及迁移限制>

## 来源与校验

- 源码标签：<tag>；完整提交：<commit>
- APK SHA-256：<最终文件哈希；无 APK 时删除>
- 签名证书 SHA-256：<最终证书指纹；无 APK 时删除>
- 校验和、许可与反馈：<对应附件及文档链接>
```

## 7. 创建草稿、上传和发布

仅在本次授权覆盖远端操作后执行本节。先完成可审阅的本地候选、说明和附件清单，逐项核对正文主题和附件的纳入依据。不属于标准范围且未经用户明确要求的内容，包括原始 JSON，必须先从待发布内容中移除；内部核验材料继续保留。

1. 再次读取远端仓库、同名标签及 Release。核对标签实际指向的完整提交；`target_commitish` 字段不能代替标签解析结果。
2. 在授权范围内推送所需源码和明确标签，核对远端结果。不得用 `git push --mirror`、强制推送或批量推送无关标签代替逐项推送。
3. 没有同名 Release 时先创建草稿，明确目标仓库、标签、预发布状态和 Latest 安排。已存在时使用其 Release ID 和实际状态继续处理；不是本次草稿时不得覆盖。
4. 只按附件清单逐项上传，回读每个附件的名称、大小、上传状态及 SHA-256，并核对远端附件集合与清单完全一致。远端提供 `digest` 时与本地比较；缺失时下载到新目录计算，不把上传命令成功当作校验完成。
5. 对照本地说明回读标题、正文和状态，核对正文和附件均属于标准范围或用户明确要求的具体项；原始 JSON 必须有针对该项的明确要求。检查上传材料与已验证候选一致。若已有完整发布授权且条件满足，直接执行发布；若仅获准草稿，则保持草稿并交付。
6. 发布后再次读取 Release ID、页面、标签提交、`draft`、`prerelease`、Latest 安排和附件清单，确认达到约定状态。从发布入口重新下载交付附件并计算 SHA-256，与本地清单比较；私有仓库使用获准的访问身份，报告其访问限制。

使用 GitHub CLI 时，显式指定 `--repo`。创建使用已有远端标签的 Release 时使用 `--verify-tag`，避免 CLI 在标签缺失时从默认分支自动建立标签；说明先写入 UTF-8 文件，再用 `--notes-file` 传入。草稿使用 `--draft`，预发布使用 `--prerelease`，预览版显式设置 `--latest=false`。参数含义见 [gh release create](https://cli.github.com/manual/gh_release_create)。

发布既有草稿会改变其可见状态；CLI 的 `gh release edit <tag> --draft=false --repo <owner/repo>` 只在发布授权内运行，其他状态仍须显式核对。相关参数见 [gh release edit](https://cli.github.com/manual/gh_release_edit)，附件 `size`、`state` 和 `digest` 字段见 [Release assets API](https://docs.github.com/en/rest/releases/assets)。

需要用户批准或仓库环境审核时，保持当前候选可审阅，明确指出批准后将改变的具体状态。不得绕过环境保护，也不为已明确授权的相同步骤再次请求批准。

## 8. 失败、重试与已发布内容的修正

| 情况 | Agent 的处理要求 |
| --- | --- |
| 本地构建或校验失败 | 保留原因，修正后重跑受影响检查；不得发布失败候选 |
| 认证、权限或环境审核受阻 | 保留本地候选和远端实际状态，说明具体受阻动作；不得关闭保护或扩大权限 |
| 网络超时、TLS 错误或上传中断 | 先查询操作是否已成功，再决定是否重试；不得直接重复创建 Release、标签或同名附件 |
| 同名草稿附件已存在 | 哈希一致则复用；不一致则核对本次允许更新的范围，更新后重新核对全部清单及校验和 |
| 发布请求返回错误，但远端已发布 | 按已发布状态核验和报告，不再创建第二个 Release；有后续问题按已发布修正处理 |
| 已发布附件错误 | 报告影响并提出撤回或新版本方案；未经明确授权，不删除 Release、移动标签或替换已发布附件 |
| 只需更正说明 | 在获准范围内更新，回读正文并确认标签、状态及附件未意外变化 |
| 草稿或已发布内容中发现未经用户明确要求的原始 JSON、额外报告或其他规范外项目 | 停止后续上传和发布，记录具体项目；本次草稿中由 Agent 添加且可在现有授权内修正的内容应移除，既有或已发布内容按对应修改授权处理，不将其视为本次默认可保留的项目 |
| 中途停止或无法完成 | 记录 Release ID、当前状态、已完成上传项、缺项和继续操作所需信息；不得报告为发布完成 |

清理只涉及本次创建、路径已经确认的临时材料，不删除用户的长期签名密钥、唯一备份、未发布成果或服务器数据。数据库升级和回滚属于独立部署操作，见[自部署指南](SELF_HOSTING.md)。

## 9. 交付结果和完成条件

Agent 最终回复必须与实际停止位置一致，至少包括：

- 本地候选位置或 Release 链接；远端 Release 的草稿、预发布及仓库可见状态。
- 标签、完整提交、客户端版本和 Android 构建号；不适用项说明原因。
- 实际交付的平台和附件、校验和位置；包含 APK 时给出签名证书指纹或其记录位置。
- 已执行检查、未执行或失败项目、仍待完成的验收；远端 CI 的提交及结果。
- 是否完成上传、发布和下载复核；如未完成，指出具体缺项及下一步。
- 正文及附件是否均符合本规范；存在用户明确要求的额外项目时，列明项目及对应要求。

文档起草完成不等于已建立远端草稿，Actions artifact 上传成功不等于 Release 已发布，Release 已发布也不等于真机或部署验收完成。只有本次约定的最终状态、来源对应、附件核验、内容范围核对及说明回读均已完成，才能报告相应发布任务完成。该要求通过项目指令和发布前后核对执行，不表示当前脚本已自动拦截所有额外内容。
